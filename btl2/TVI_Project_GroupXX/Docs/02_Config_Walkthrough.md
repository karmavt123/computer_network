## 2. Layer 2 - HQ core and access

Rubric step 3. HQ has a real switched campus; the branches use one access switch dual-homed to the two edge routers.

### 2.1 VLAN database and deterministic RSTP roots

From `HCMC-CORE-SW01.cfg`:

```text
spanning-tree mode rapid-pvst
spanning-tree extend system-id
spanning-tree vlan 10,30,50,90,99,100 priority 4096
spanning-tree vlan 20,40,60 priority 8192
spanning-tree loopguard default
errdisable recovery cause bpduguard psecure-violation
errdisable recovery interval 300
```

**What.** Rapid-PVST+ with the root bridge pinned by priority: CORE-SW01 is root (4096) for one VLAN group and secondary (8192) for the other; CORE-SW02 is the mirror image. Loop guard is on globally.

**Why.** The root bridge decides which uplink of each access switch forwards. It is placed on the same switch that is HSRP active for the VLAN (see 3.1), so a frame is switched to the root and routed there - it never crosses Po1 just to reach its gateway. Splitting the VLANs between the two cores uses both uplinks of every access switch instead of leaving half the links idle. RSTP was kept instead of MST because the VLAN count is small; the report explains when MST becomes the better choice.

**Verify.** `show spanning-tree root` on both cores (each says "This bridge is the root" for its group); on an access switch `show spanning-tree vlan 10` shows one Root port and one Alternate (blocking) port.

**Without it.** The switch with the lowest MAC becomes root - possibly an access switch - and all inter-VLAN traffic takes a sub-optimal path; a rogue switch could take over the role.

### 2.2 LACP EtherChannel between the cores (Po1)

From `HCMC-CORE-SW01.cfg`:

```text
interface Port-channel1
 description PO1 LACP to HCMC-CORE-SW02
 switchport trunk encapsulation dot1q
 switchport mode trunk
 switchport trunk native vlan 998
 switchport trunk allowed vlan 10,20,30,40,50,60,90,99,100
 switchport nonegotiate
 no shutdown
interface GigabitEthernet0/0
 description PO1 member -> HCMC-CORE-SW02 Gi0/0
 switchport trunk encapsulation dot1q
 switchport mode trunk
 switchport trunk native vlan 998
 switchport nonegotiate
 channel-protocol lacp
 channel-group 1 mode active
 no shutdown
```

**What.** Two physical links bundled with LACP (`mode active` on both ends) into one logical trunk. Native VLAN 998 carries no hosts; DTP is disabled (`nonegotiate`).

**Why.** The brief requires EtherChannel on core links. One Po1 member can fail without a spanning-tree topology change and without losing the VLAN 90 transit between the cores. LACP (not `mode on`) detects a mis-cabled or one-way member instead of black-holing traffic on it.

**Verify.** `show etherchannel summary` -> `Po1(SU)` with `Gi0/0(P) Gi0/1(P)`; shut one member: ping keeps running, the summary shows one (P) and one (D).

**Without it.** A single inter-core link is a single point of failure for every VLAN whose root and HSRP-active roles sit on different sides after a failure.

### 2.3 Core-to-access trunk with root guard

From `HCMC-CORE-SW01.cfg`:

```text
interface GigabitEthernet0/2
 description TRUNK -> HCMC-ACC-SW01 Gi0/0
 switchport trunk encapsulation dot1q
 switchport mode trunk
 switchport trunk native vlan 998
 switchport trunk allowed vlan 10,20,30,40,50,60,99,100
 switchport nonegotiate
 spanning-tree guard root
 no shutdown
```

**What.** 802.1Q trunk to an access switch, only the VLANs that exist at the access layer are allowed, and `spanning-tree guard root` on the core side.

**Why.** "Root bridge enforcement" is an explicit rubric item. Priority alone is not enforcement: a switch plugged in with priority 0 would win. Root guard puts the port into *root-inconsistent* state the moment a superior BPDU arrives.

**Verify.** `show spanning-tree inconsistentports` (empty in normal operation). Optional proof: set `spanning-tree vlan 10 priority 0` on an access switch - the core port goes root-inconsistent and recovers when the change is removed.

**Without it.** Any device at the access layer can become root for a VLAN.


**What.** DHCP snooping and Dynamic ARP Inspection on the user VLANs; uplinks are *trusted*, user ports are not. A user port is a fixed access port with PortFast + BPDU guard, port security (2 sticky MACs, `restrict`) and broadcast storm-control. Option 82 insertion is disabled because the relay is the L3 gateway, not this switch.

**Without it.** A PC running a DHCP server or ARP spoofing tool can redirect a whole VLAN through itself.

Rubric step 4.

### 3.1 HSRPv2 gateway on a core SVI - active side

From `HCMC-CORE-SW02.cfg`:

```text
track timer ip route 1
track 1 ip route 0.0.0.0 0.0.0.0 reachability
interface Vlan20
 description RND_ENGINEERING gateway
 ip address 10.1.4.3 255.255.252.0
 ip helper-address 10.1.100.10
 ip access-group ACL-CORP-IN in
 ipv6 address 2001:db8:1:20::3/64
 ipv6 nd other-config-flag
 ipv6 dhcp relay destination 2001:db8:1:100::10
 ipv6 traffic-filter ACL6-CORP-IN in
 ip ospf 10 area 0
 ospfv3 10 ipv6 area 0
 standby version 2
 standby 20 ip 10.1.4.1
 standby 20 priority 110
 standby 20 preempt delay minimum 60
 standby 20 timers msec 500 msec 1500
 standby 20 authentication md5 key-string TVI-HSRP-Lab-2026
 standby 20 track 1 decrement 30
 standby 1020 ipv6 autoconfig
 standby 1020 ipv6 2001:db8:1:20::1/64
 standby 1020 priority 110
 standby 1020 preempt delay minimum 60
 standby 1020 timers msec 500 msec 1500
 standby 1020 authentication md5 key-string TVI-HSRP-Lab-2026
 standby 1020 track 1 decrement 30
 no shutdown
```

**What.** The default gateway of VLAN 20 is the *virtual* address `.1`; this switch owns it (priority 110). DHCP requests are relayed to the central server (`ip helper-address`), the inbound ACL enforces segmentation, and a second group (number + 1000 - an HSRP group has one address family) provides the IPv6 virtual gateway with identical settings. Hellos every 500 ms, hold 1.5 s, MD5 authentication. `preempt delay minimum 60`: after a reboot the switch waits a minute (routing must converge first) before it takes the role back. Track object 1 lowers the priority by 30 if the switch has no default route at all.

**Why.** "FHRP must be configured for default gateway redundancy" - and four-nines availability means a core switch may fail without any host noticing more than a couple of seconds. HSRPv2 (not v1) is required for IPv6 and millisecond timers. The 30-point decrement is larger than the 10-point priority gap, so tracking really moves the role.

**Verify.** `show standby brief` on both cores: complementary Active/Standby, `P` flag set. `show track`.

**Without it.** Hosts point at one physical switch; when it fails every host in the VLAN loses its gateway until someone reconfigures them.

## 4. Underlay routing - OSPF / OSPFv3

Rubric step 5. Each site is its own OSPF domain (area 0); sites never exchange OSPF routes with each other.

### 4.1 OSPF on a core switch

From `HCMC-CORE-SW01.cfg`:

```text
router ospf 10
 router-id 10.1.255.1
 passive-interface default
 no passive-interface Vlan90
 no passive-interface GigabitEthernet1/0
 no passive-interface GigabitEthernet1/1
 auto-cost reference-bandwidth 10000
router ospfv3 10
 router-id 10.1.255.1
 address-family ipv6 unicast
  passive-interface default
  no passive-interface Vlan90
  no passive-interface GigabitEthernet1/0
  no passive-interface GigabitEthernet1/1
  auto-cost reference-bandwidth 10000
 exit-address-family
```

**What.** One OSPF process, area 0, enabled per interface (`ip ospf 10 area 0`). `passive-interface default` means no hello is ever sent towards users; only the inter-core transit (VLAN 90) and the two routed uplinks form adjacencies. OSPFv3 with the IPv6 address family mirrors it. Reference bandwidth 10 Gbit/s keeps 1G and 10G links distinguishable.

**Why.** The brief prescribes OSPF inside a site. A single area is correct for this size (a handful of routers per site); areas would add ABRs and summarisation without any benefit. Passive-by-default removes the risk of a rogue OSPF speaker in a user VLAN.

**Verify.** `show ip ospf neighbor` (FULL with the peer core and both edges), `show ip route ospf` (the default route is `O*E1`), `show ospfv3 neighbor`.

**Without it.** Without passive-default a PC running a routing daemon can inject routes.

### 4.2 Conditional default route from the HQ edge

From `HCMC-EDGE-RTR01.cfg`:

```text
router ospf 10
 router-id 10.1.255.11
 passive-interface default
 auto-cost reference-bandwidth 10000
 no passive-interface GigabitEthernet0/1
 no passive-interface GigabitEthernet0/2
 no passive-interface GigabitEthernet0/3
 default-information originate metric 10 metric-type 1
```

**What.** The edge router advertises `0.0.0.0/0` into OSPF as an external type-1 route with seed metric 10 (EDGE-RTR02 uses 20) - **without** the `always` keyword.

**Why.** Type 1 adds the internal cost, so the choice between the two edges is deterministic (10 beats 20). Without `always` the default is advertised only while the router itself has one (learned by eBGP from its ISP): when ISP-A fails, EDGE-RTR01 withdraws the default and the cores switch to EDGE-RTR02 by themselves.

**Verify.** `show ip route 0.0.0.0` on a core -> via EDGE-RTR01. Shut EDGE-RTR01 Gi0/0: the route changes to EDGE-RTR02 (metric 20 + cost).

**Without it.** With `always`, the cores would keep sending Internet traffic to an edge that has lost its ISP.

### 4.3 Edge-to-edge routed link at HQ

From `HCMC-EDGE-RTR01.cfg`:

```text
interface GigabitEthernet0/3
 description L3 -> HCMC-EDGE-RTR02 Gi0/3 (edge-to-edge: iBGP next-hops never transit the core)
 ip address 10.1.250.17 255.255.255.252
 ipv6 address 2001:db8:1:fa05::1/64
 ip nat inside
 zone-member security INSIDE
 ip ospf network point-to-point
 ip ospf 10 area 0
 ip ospf hello-interval 1
 ip ospf dead-interval 4
 ospfv3 10 network point-to-point
 ospfv3 10 ipv6 area 0
 ospfv3 10 hello-interval 1
 ospfv3 10 dead-interval 4
 no shutdown
```

**What.** A direct /30 between the two HQ edge routers, in OSPF.

**Why.** The core switches run no BGP: they only know "default -> EDGE-RTR01". If EDGE-RTR01 loses the tunnel to a branch but keeps its ISP default, BGP tells it to reach the branch through EDGE-RTR02. Without this link the only path between the edges is through a core - which looks up the branch address, finds only the default route, and sends the packet straight back: a routing loop. With the link, the iBGP next hop (EDGE-RTR02's loopback) is one hop away and never transits the core. The FRR emulation reproduces both cases (scenario S2 with the link, S9 without).

**Verify.** `show ip ospf neighbor` on an edge lists the other edge on Gi0/3; `show ip route 10.1.255.12` -> via Gi0/3.

**Without it.** A single branch-ISP failure cuts HQ off from that branch although a backup tunnel is up.

### 5.1 GRE tunnel protected by IPsec (hub side)

From `HCMC-EDGE-RTR01.cfg`:

```text

interface Tunnel1
 description GRE/IPsec to HANOI-EDGE-RTR01 via ISP-A

 ipv6 address 2001:db8:ff:1::1/64
 ip mtu 1400
 ip tcp adjust-mss 1360

 ipv6 tcp adjust-mss 1340
 tunnel source GigabitEthernet0/0
 tunnel mode gre ip
 tunnel destination 203.0.113.6
 tunnel protection ipsec profile TVI-IPSEC-PROFILE
 zone-member security VPN
 no shutdown
```

**What.** IKEv1 with a pre-shared key per peer (AES-256, SHA-256, DH group 14), an IPsec profile in transport mode, and one GRE tunnel interface per branch protected by that profile. The tunnel is a routed /30 (+ an IPv6 /64), so BGP simply runs across it; dead-peer detection is enabled. MTU/MSS are lowered to leave room for the GRE and ESP headers.

**Why.** The brief asks for IPsec tunnels over the dual-ISP underlay, and for dual-stack. A tunnel *interface* (rather than a crypto map) gives routing protocols, QoS and the firewall zone something to attach to. GRE is used inside IPsec because one GRE tunnel carries IPv4 and IPv6 (and multicast); an IKEv1 `tunnel mode ipsec ipv4` VTI carries IPv4 only, which would leave the IPv6 BGP sessions down. HQ is the hub because the data centre is there; four tunnels (2 branches x 2 ISPs) instead of a full mesh.

**Verify.** `show crypto isakmp sa` (QM_IDLE), `show crypto ipsec sa | include encaps|decaps` (counters grow), `show interface Tunnel1` (Tunnel protocol/transport GRE/IP, protection IPsec), `ping ipv6` across the tunnel.

**Without it.** Inter-site traffic would cross the Internet in clear text - unacceptable for Executive/Finance data.

```text
  neighbor 203.0.113.1 prefix-list PL-ISP-IN in
  neighbor 203.0.113.1 prefix-list PL-NONE-OUT out
  neighbor 10.1.255.12 activate
  neighbor 10.1.255.12 next-hop-self all
  neighbor 10.1.255.12 prefix-list PL-TVI-AGG out
  neighbor 10.255.1.2 activate
  neighbor 10.255.1.2 prefix-list PL-TVI-AGG out
  neighbor 10.255.1.2 route-reflector-client
  neighbor 10.255.1.2 next-hop-self all
  neighbor 10.255.1.10 activate
  neighbor 10.255.1.10 prefix-list PL-TVI-AGG out
  neighbor 10.255.1.10 route-reflector-client
  neighbor 10.255.1.10 next-hop-self all
 exit-address-family
 !
```

**What.** eBGP to the ISP: accept only a default route, advertise nothing (the site uses private addresses behind NAT). iBGP to the other HQ edge (loopback to loopback) and to each branch over its tunnel. The branches are route-reflector clients. `next-hop-self all` rewrites the next hop even on reflected routes. Hold time 9 s on every session. The site aggregate is originated with a `network` statement anchored by a static route to Null0.

**Why.** BGP is prescribed for inter-site and ISP routing. Route reflection removes the need for a full iBGP mesh between six edge routers. Only three aggregates exist enterprise-wide, so the BGP table stays tiny however many VLANs are added. The 3/9 s timers bound failure detection to 9 s; they are also needed on the edge-to-edge session because the peer's loopback lies inside the Null0 summary, so next-hop tracking alone would keep a dead peer's routes (found with the FRR emulation, scenario S3).

**Verify.** `show ip bgp summary` (all Established), `show ip bgp` (`10.2.0.0/16` and `10.3.0.0/16` with local-pref 200 via the tunnels), `show ip bgp neighbors <branch> advertised-routes`.

**Without it.** No dynamic inter-site routing; static routes would not fail over.

### 5.4 Summary anchor and NAT overload (local Internet breakout)

From `HANOI-EDGE-RTR01.cfg`:

```text
ip route 10.2.0.0 255.255.0.0 Null0 name TVI-HANOI-SUMMARY
ipv6 route 2001:db8:2::/48 Null0 name TVI-HANOI-SUMMARY6
ip nat inside source list ACL-NAT interface GigabitEthernet0/0 overload
ip access-list extended ACL-NAT
 remark never translate corporate-to-corporate traffic (fails closed if the VPN is down)
 deny   ip 10.0.0.0 0.255.255.255 10.0.0.0 0.255.255.255
 permit ip 10.0.0.0 0.255.255.255 any
```

**What.** The Null0 static makes the /16 exist in the routing table (BGP only originates what is there) and discards traffic for unused parts of the block. NAT overload translates private sources to the WAN address - except corporate-to-corporate traffic, which must use the tunnel.

**Why.** "Direct cloud access from branch offices without backhauling through HQ": every edge router has its own default route from its own ISP and its own NAT, so SaaS traffic leaves at the branch. Denying 10/8-to-10/8 in the NAT ACL means inter-site traffic fails closed (it is dropped, not leaked to the Internet) if the VPN is down.

**Verify.** From a Hanoi PC: `ping 8.8.8.8`; on HANOI-EDGE: `show ip nat translations` shows the entry, the HQ edge shows none; `trace 8.8.8.8` has no HQ hop.

**Without it.** All branch Internet traffic would hairpin through HQ (latency, HQ bandwidth, single dependency).

## 6. Security policy

Rubric step 7. Layer-2 security is in section 2.

### 6.1 Segmentation ACLs: guests and IoT

From `HCMC-CORE-SW01.cfg`:

```text
ip access-list extended ACL-GUEST-IN
 remark Guests: DHCP + Internet only, no RFC1918 destination at all
 permit udp any eq bootpc any eq bootps
 permit udp any host 224.0.0.102 eq 1985
 deny   ip any 10.0.0.0 0.255.255.255
 deny   ip any 172.16.0.0 0.15.255.255
 deny   ip any 192.168.0.0 0.0.255.255
 permit ip any any
ip access-list extended ACL-IOT-IN
 remark IoT: DHCP/DNS/NTP + IoT platform (MQTT-TLS/HTTPS) only; no lateral movement, no Internet
 permit udp any eq bootpc any eq bootps
 permit udp any host 224.0.0.102 eq 1985
 permit udp any host 10.1.100.10 eq domain
 permit udp any host 10.1.100.10 eq ntp
 permit icmp any host 10.1.100.10 echo
 permit tcp any host 10.1.100.20 eq 8883
 permit tcp any host 10.1.100.20 eq 443
 permit tcp any any established
 permit icmp any any echo-reply
 deny   ip any any log
```

**What.** Inbound ACLs on the gateway interface of each VLAN. Guests: DHCP and HSRP hellos, then *deny every private destination*, then permit the rest (= Internet). IoT: DHCP, DNS/NTP and ping to the infrastructure server, MQTT-over-TLS and HTTPS to the IoT platform, replies to sessions opened from outside, then deny and log.

**Why.** The rubric item is "ACLs isolating Guest from Corp"; the brief adds IoT. Filtering *inbound at the first L3 hop* stops unwanted traffic before it is routed anywhere. IoT devices are the least patchable systems on the network, so they get an allow-list: they can talk to their platform and nothing else - no lateral movement, no Internet.

**Verify.** Guest PC: `ping 8.8.8.8` works, `ping 10.1.100.10` fails. `show access-lists ACL-GUEST-IN` - the deny counters increase. IoT PC: only `ping 10.1.100.10` works.

**Without it.** One compromised sensor or visitor laptop can reach finance systems.

### 7.1 Classification, re-marking and the WAN queueing policy

From `HCMC-EDGE-RTR01.cfg`:

```text
ip access-list extended QOS-VOICE-RTP
 permit udp 10.1.12.0 0.0.3.255 any range 16384 32767
 permit udp 10.2.12.0 0.0.3.255 any range 16384 32767
 permit udp 10.3.8.0 0.0.1.255 any range 16384 32767
ip access-list extended QOS-VIDEO
 permit udp 10.0.0.0 0.255.255.255 any range 3478 3481
ip access-list extended QOS-SIGNALING
 permit tcp 10.0.0.0 0.255.255.255 any eq 5060
 permit tcp 10.0.0.0 0.255.255.255 any eq 5061
 permit tcp 10.0.0.0 0.255.255.255 any eq 2000
 permit udp 10.0.0.0 0.255.255.255 any eq 5060
class-map match-any CM-IN-VOICE
 match access-group name QOS-VOICE-RTP
class-map match-any CM-IN-VIDEO
 match access-group name QOS-VIDEO
class-map match-any CM-IN-SIGNALING
 match access-group name QOS-SIGNALING
policy-map PM-MARK-IN

  set dscp ef
 class CM-IN-VIDEO
  set dscp af31
 class CM-IN-SIGNALING
  set dscp cs3
 class class-default
  set dscp default
class-map match-any CM-VOICE
 match dscp ef
class-map match-any CM-VIDEO
 match dscp af31
class-map match-any CM-SIGNALING
 match dscp cs3
class-map match-any CM-NET-CTRL
 match dscp cs6
policy-map PM-WAN-CHILD
 class CM-VOICE
  priority percent 20
 class CM-VIDEO
  bandwidth percent 25
 class CM-SIGNALING
  bandwidth percent 5
 class CM-NET-CTRL
  bandwidth percent 5
 class class-default
  fair-queue
policy-map PM-WAN-PARENT
 class class-default
  shape average 20000000
  service-policy PM-WAN-CHILD
interface GigabitEthernet0/0
 description WAN -> ISP-A-RTR Gi0/0 (203.0.113.0/30)
 ip address 203.0.113.2 255.255.255.252
 ip nat outside
 zone-member security OUTSIDE
 ip verify unicast source reachable-via rx allow-default
 service-policy output PM-WAN-PARENT

```

**What.** Inbound (`PM-MARK-IN`, on LAN-facing interfaces): voice RTP from the voice VLANs -> EF, video -> AF31, signalling -> CS3, everything else reset to 0. Outbound on the WAN (`PM-WAN-PARENT`): shape to the contracted rate, and inside the shaper give voice a strict-priority queue (20 %), video 25 %, signalling 5 %, network control 5 %, the rest fair-queued.

**Why.** "Voice traffic must be prioritized over all WAN links." Marking is decided by the network (source VLAN + ports), never by the endpoint, so a PC cannot promote itself. The shaper is essential: an Ethernet hand-off never congests at the interface, so without shaping to the circuit rate the queues would never form and the ISP would drop packets blindly. IPsec copies the inner DSCP to the outer header, so the policy still sees the marking after encryption.

**Verify.** `show policy-map interface gi0/0 output` before and after `ping <branch loopback> source lo0 repeat 300 tos 184` - the `CM-VOICE` counters grow; under load only `class-default` shows drops.

**Without it.** Voice competes with bulk transfers on the WAN: jitter and loss during every busy period.

## 8. After pasting a config

Every file ends with two exec-mode commands that cannot live in a startup-config:

```text
crypto key generate rsa general-keys modulus 2048
copy running-config startup-config
```

The RSA key is what turns SSH on; without it the automation cannot connect.
